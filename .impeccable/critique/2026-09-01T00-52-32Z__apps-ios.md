## Design Specificity Verdict

**Start here.** The player and book objects are authored for Rawkoon. The chrome around them is a web homepage wearing TabView.

**LLM assessment:** A warm brown room, a spine on the cover, a chapter rail, and terracotta→apricot progress are not a generic streaming shell. That identity lives in `Theme.swift`, `PlayerView`, `BookCover`, `SpineRow`, and `DuskProgress`. Around those objects, `HomeView` is the browser dashboard (greeting, Recently added, Upcoming, Continue, Now watching, Downloads, Needs attention, RSS). `RootTabsView` puts that dashboard in front of the four PRODUCT/DESIGN sections as a fifth tab. Discover is a TMDB poster mall with an apricot plus on every card. Media detail is a five-lane *arr console. Three tells: (1) `BookCover`’s left spine strip and `SpineRow`’s lit capsule exist only in this product. (2) `HomeView`’s widget stack is the web homepage, not a bedside remote. (3) `DiscoverView.statusChip` paints `Theme.apricot` on every not-in-library poster while `Appearance.apply()` also fills every selected segment apricot — the lamp is a floodlight.

**Deterministic scan:** Detector ran on `apps/ios` and returned `[]` (exit 0). It only walks HTML/CSS/JS-family extensions. **Visual overlays:** No reliable user-visible overlay. Overlay injection is not applicable to native SwiftUI on Linux (no web surface, `live-server.mjs` not started). Simulator screenshots skipped: `xcrun` not found. Fallback signal: CLI `[]` on a non-UI TypeScript script.

## Overall Impression

Now Playing is the product. Everything that leads there — five-tab IA, a web Home, Request buried on Actions, apricot on every chip — fights the bedside job. The single biggest opportunity is to make the phone the remote and the player: four tabs, Request on the hero, apricot only on Play.

## What's Working

1. **`PlayerView` + `MiniPlayerView` + `Theme.duskGlow`** — native sheet, drag indicator, 66pt play, on-accent glyph, terracotta pressed, mono times, a11y labels on transport. This is Cozy Dusk, not a skin.
2. **Signature objects in `Components.swift`:** `BookCover` spine, `SpineRow` current/downloaded/hollow, `DuskProgress` well. Chapter download state is visible without reading.
3. **Native structure and admin gating:** `TabView` / `NavigationStack` / sheets / `confirmationDialog` / swipe actions on `RequestsView`; Settings Admin section is `if model.isAdmin`. Household is not handed indexer forms.

## Cognitive load

7 of 8 checklist items fail — **high**. Failed: single focus, chunking, visual hierarchy, one thing at a time, minimal choices, working memory, progressive disclosure. Passed: grouping (Settings Form sections, Activity Queue/History/Calendar, Book lanes).

## Emotional journey

Peak is `PlayerView`. Valley is first launch into `HomeView` admin telemetry, then hunting `Actions` to Request, then a control-farm `ReleaseSearchView` whose grab failure erases the list. After a request, the end is a `"Requested"` badge and silence — no “we’ll notify you,” path only via Settings → Requests. Library remove is the one high-stakes flow that is reassured.

## Priority Issues

### [P1] Fifth tab: Home is a web dashboard in front of the product IA
- **What:** `RawkoonApp.swift` `mainTabs` is Home / Discover / Library / Activity / Settings. PRODUCT.md and DESIGN.md specify Discover / Library / Activity / Settings. `HomeView` uses an empty `.navigationTitle("")` plus a logo principal, not a large title.
- **Why it matters:** Default land is admin telemetry (RSS, Needs attention, download speeds, Jellyfin “Now watching”). Household members start in the wrong building. Five tabs break “sections, not actions” and “do not invent a fifth tab.”
- **Fix:** Delete the Home tab. Fold Continue into Library (or a Library header). Fold Downloads/Attention/RSS into Activity. Keep Discover as tab 0.
- **Suggested command:** `$impeccable distill`

### [P1] Request is hidden; Requests is a Settings orphan
- **What:** Household primary action is `MediaDetailView.actionsTab` → `"Request"` / `"Add to library"`, behind a segmented control. After success, `StatusBadge("Requested")`. To see the queue: Settings → `RequestsView`. Discover `statusChip` plus looks like Add but is a non-interactive overlay on a `NavigationLink`.
- **Why it matters:** Jordan will tap plus, land on Info, never find Actions, never find Settings → Requests. Casey will not hunt a third segment one-handed.
- **Fix:** Put Request/Add on the Info hero as the one primary control. Surface pending requests on Library or Activity, not only Settings. Make plus a real control or stop drawing it as one.
- **Suggested command:** `$impeccable onboard`

### [P1] One Lamp Rule is broken; Importing is used as format chrome
- **What:** Apricot fills tab tint, every selected segment, Discover/Similar plus circles, Login Sign In, Home continue chevrons, Library downloading badge, pending request badges, every Grab, HDR, Admin, Audiobook chips, and BookView Play *and* Download *and* Search. `Theme.importing` paints EPUB chips, Read, Add EPUB, and file Download — status blue used as a second brand. Home upload speed uses `Theme.seed`.
- **Why it matters:** If everything is lit, Now Playing’s lamp means nothing. Semantic hues stop meaning “in library / inbound.”
- **Fix:** Apricot fill only on Play (and the single focused primary). Selected segments → raised/terracotta hairline. Plus → muted. EPUB/Read → parchment/terracotta, never Importing. Seed only on in-library / seeder counts.
- **Suggested command:** `$impeccable quieter`

### [P1] Discover cannot find books
- **What:** `DiscoverView.KindFilter` is All / Movies / TV. Placeholder: `"Search movies & shows"`. No Google Books path. Books exist only under Library after they are already in the instance.
- **Why it matters:** The phone is supposed to be the front-end for the whole instance. Household cannot request or even search a book from Discover.
- **Fix:** Add Books to the kind picker and search; poster vs `BookRow` can differ, but the entry point cannot.
- **Suggested command:** `$impeccable shape`

### [P1] Grab failure destroys the sheet; destructive Settings are unguarded
- **What:** `ReleaseSearchView.grab` catch sets `errorMessage`, and `content` treats any `errorMessage` as full-screen `"Search failed"`, replacing the list. Same pattern in `BookReleaseSearchView`. Settings `"Delete Downloads"` and `"Log Out"` are immediate. Grab itself has no confirm.
- **Why it matters:** The most expensive click (hand a torrent to qBittorrent) has no “are you sure” and the failure mode erases the decision set. Delete Downloads wipes bedside offline chapters.
- **Fix:** Keep the list; attach a row-level error. Confirm Delete Downloads / Log Out. Do not reuse `errorMessage` for search-fail vs grab-fail.
- **Suggested command:** `$impeccable harden`

## Persona Red Flags

**Casey (one-handed, bedside, interrupted):** Mini-player play is 30×30 nested inside an expand button. Now Playing has no chapter list (dismiss sheet → `BookView` spine). Sleep menu is seven items. Ebook chrome is 34×34 and auto-hides in 3s; failed open has no Close. Discover plus chips sit top-trailing, outside the thumb zone, and are not the tap target.

**Jordan (household first-timer):** Lands on Home widgets (“Download client offline.”, “No RSS runs yet.”). Discover search cannot find books; plus does not request. Media detail Info has no Request; must open Actions. After Request, no explanation of grab/import. `"EPUB"` vs product language `ebook`. Cannot see “your request is pending” without Settings.

**Alex (homelab admin):** Quality profiles, indexers, users, download client are read-only. Activity queue cards have no Pause/Remove; no `.refreshable`. Release search is the power tool and the overload; grab fail wipes that work. Context menus are the real accelerator, buried on long-press. Fifth tab is an extra hop to Discover.

**Morgan (household regular — PRODUCT’s second audience):** Continue on Home is the right object on the wrong tab, capped at six, with apricot chevrons on every row. Audiobook Play on `BookView` is a wide prominent button, not the 66pt lamp. Library starts on `"Media"`; books are a segment. Notifications: 16 toggles including `github_release` / `app_update`.

## Minor Observations

- Every top-level screen sets `.navigationBarTitleDisplayMode(.inline)` — DESIGN wants large titles on Discover, Library, Activity, Settings.
- `Font.display(_:)` and `Appearance.apply()` hard-code 13–40pt; Native Type Rule is not followed outside a few system styles.
- Touch targets under 44pt: `PosterFlag` 22, Discover plus 22, mini-player play 30, bookmark 34, reader controls 34, filter chips, Grab, `"Load more"` height 28.
- `ActivityView` history dots use `.red`, not terracotta.
- Discover feed is not `.refreshable`; errors are `"Server error (\(status))"`.
- `MediaPosterCard` titles at `Font.display(13)` put Fraunces on captions.
- Calendar in Activity uses `BookCover` (spine) on movie posters.
- `HomeView` continue ebook progress says `"Page \(spineIndex)"` — spine ≠ page.
- Reader `ReaderTheme.light` / `.sepia` vs Dark-Only Rule (reading exception is defensible).
- Login password eye unlabeled; no passkey affordance despite `WebAuth.swift`.

## Questions to Consider

- If the iPhone is the remote for video and the player for audiobooks, why is tab 0 a homelab status board copied from the web homepage?
- What would happen if Request sat on the poster and the Info hero, and “my requests” sat on Library — and Settings stopped being a place people live?
- If apricot appeared only on the playing control, would Discover still feel like Rawkoon, or would you finally see the lamp?
- Should Now Playing own chapters (the spine lives on `BookView` today), or is the signature screen allowed to be incomplete at the bedside?
- Grab is the irreversible handoff to the download client: why does a failed grab look identical to “search failed”?
