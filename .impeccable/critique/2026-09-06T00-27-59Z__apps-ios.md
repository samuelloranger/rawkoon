## Design Specificity Verdict

**Authored, not category-interchangeable.** Held against its own committed Cozy Dusk system, this reads as a specific object — a dim warm-brown room with one apricot lamp. Evidence is in the discipline, not the palette declaration:

- `Theme.swift:12-39` encodes the spec faithfully (warm surfaces, apricot lamp, terracotta-pressed, on-accent dark ink, semantic-only sage/steel), and Fraunces is gated behind a `display()` helper (`Theme.swift:62-67`) that *cannot* land on body without a deliberate call.
- **The One Lamp Rule is enforced in code, not aspirational**: apricot *fills* appear only on Play (`PlayerView.swift:463-471`, `MiniPlayerView.swift:47`); every other primary is terracotta (`MediaDetailView.swift:409`, `BookView.swift:745`, `LoginView.swift:93`). The live screenshot confirms it — one apricot Play, terracotta outlined Download/Search-releases.
- Signature components do real narrative work: BookCover spine strip + terracotta→apricot placeholder (`Components.swift:16-26`), DuskProgress terracotta→apricot fill that never falls to system blue (`Components.swift:68-83`), SpineRow lit current chapter with apricot glow (`Components.swift:235-244`).

Reservation: the admin Management tab (`MediaDetailView.swift:522+`) and Settings admin list (`SettingsView.swift:73-208`) are utilitarian *arr tooling that could belong to any downloader. The *bedside* surfaces (Player, Mini-player, Home, Continue, Book detail) carry the identity; the *admin* surfaces don't.

**Deterministic scan** — where the two assessments agree, disagree, and one caught what the other missed:

- **Token drift (B caught, A missed):** the dark on-seed color `0x10231A` is hardcoded three times outside the theme — `Components.swift:163`, `DiscoverView.swift:393`, `MediaDetailView.swift:511` — plus a one-off gradient hex `0x2A201B` at `LoginView.swift:14`. Invisible to a screenshot (renders correctly); only cross-file grep surfaces the copy-paste. Should be a named `Theme.onSeed` token.
- **Reduce Motion zero coverage (B caught, A under-weighted):** all 3 animation sites (`RawkoonApp.swift:63`, `Toast.swift:38`, `EbookReaderView.swift:219`) ignore `accessibilityReduceMotion`. Cannot appear in a static screenshot.
- **MiniPlayer close button (B corrected A):** `MiniPlayerView.swift:56-59` is `frame(width: 34, height: 44)` with `.contentShape(Rectangle())` clamped to that frame — tap target is **34pt wide**, under the 44pt HIG minimum on the horizontal axis. A read it as "height 44, fine"; B read the contentShape/frame pairing and found the width fails. Confirmed violation.
- **Dynamic Type (both agree):** A's P1 (fixed 34pt caption boxes + lineLimit(2)) is corroborated by B's 25 `lineLimit(1)` / 0 `minimumScaleFactor` hits in list rows — truncation-prone at large text.
- **False positives cleared:** 17 hex inside Theme.swift (correct, it's the source of truth), 20 hardcoded font sizes (SF Symbol glyph sizes + Now Playing, legit display moments), `.white.opacity(.05-.08)` hairlines, `Image("AppLogo")` brand asset, most sub-44pt frames (badges/dots/handles, non-interactive). 182 `Text("...")` literals ARE auto-extractable (7106-line xcstrings catalog exists); the real ~310-string localization gap is custom components taking `String` not `LocalizedStringKey`, which grep structurally can't detect.

## Overall Impression

A genuinely well-authored app carrying its identity in code, not just docs. The design system is real and enforced. The gaps are not aesthetic — they're **accessibility (Dynamic Type + Reduce Motion + contrast), first-run, and error recoverability**. Biggest single opportunity: the app is beautiful for someone already logged in with default text size; it degrades for large-text users and abandons the first-timer at the login field. Fix the accessibility floor and the onboarding valley and this ships as a 36+.

## What's Working

1. **One Lamp Rule enforced in code** (`PlayFillStyle` `PlayerView.swift:463-471`) — apricot rarity preserved exactly, so Play reads as the one active thing.
2. **Signature components do narrative work** — DuskProgress + SpineRow lit-spine (`Components.swift:68-83, 235-244`) are a consistent "progress toward the lamp" language, not decoration.
3. **Error-resilience is unusually mature** — keep-stale-on-refresh-failure (`DiscoverView.swift:136-148`), transport-error suppression, offline cache fallback (`BookView.swift:1007,1137`), synchronous double-tap guard (`Toast.swift:99-104`). Reassurance engineered, not hoped.

## Priority Issues

**[P1] Dynamic Type clips poster titles and truncates segmented controls — `adapt`**
Poster captions use fixed `.frame(height: 34)` + `.font(.caption)` + `lineLimit(2)` (`Components.swift:143-149`, `DiscoverView.swift:377-383`, `HomeView.swift:196-199`); at accessibility text sizes the box doesn't grow and titles clip mid-word across the two densest grids (Library, Discover). Segmented pickers (`DiscoverView.swift:122-130`, `MediaDetailView.swift:350-358`) truncate to "…" at large text. *Fix:* flexible min-height + `minimumScaleFactor(0.8)` on captions; `Menu`/scrollable fallback above a size threshold for pickers.

**[P1] Errors vanish — 3s unrecoverable toasts as the primary error surface for a download manager — `harden`**
`ToastOverlay` is `allowsHitTesting(false)` (`Toast.swift:37`), every toast auto-clears at 3s (`AppModel.swift:314`), new replaces old (no queue). A failed grab/monitor/remux surfaces only here, then is gone before a distracted user looks up. For an app whose whole job is long-running background work that fails in interesting ways, this is the wrong primary error surface. *Fix:* longer duration for `.error`, swipe-to-dismiss, and route failures into the notifications list so they're recoverable.

**[P2] Settings admin is a 22-item wall — `distill`**
`SettingsView.swift:73-208` is one flat "Admin" section, 22 NavigationLinks, no sub-grouping, no search. Recall-heavy, fails "minimal choices per decision," and it's the screen that feels most like generic *arr tooling. *Fix:* chunk into Integrations / Library & Quality / Users & Security / Jobs & Releases; consider searchable.

**[P2] Non-admin household member dead-ends on book search — `onboard` / `clarify`**
In `DiscoverView.bookSearchRow` (`DiscoverView.swift:298-316`), a book hit shows "In library" badge, else "Add" *only if isAdmin*, else **nothing** — no Request path. Movies/TV give non-admins a Request (`MediaDetailView.swift:401`); books don't. A browse-only member finds a book and can do nothing. *Fix:* give non-admins a Request affordance on book hits mirroring the media flow.

**[P2] Onboarding valley + token drift — `onboard` (login) / `polish` (tokens)**
First screen asks a non-technical person to type `https://your-rawkoon-server` with zero help, discovery, or first-run (`LoginView.swift:36`). Separately, `0x10231A` is hardcoded 3× and `0x2A201B` once outside Theme.swift — token drift the theme file exists to prevent. *Fix:* server-URL help text / discovery on login; promote the copied colors to `Theme.onSeed` and the gradient stop into Theme.

**[P3] Accessibility floor: Reduce Motion, contrast, MiniPlayer target — `harden` / `polish`**
(a) Reduce Motion never checked — 3 animation sites ignore `accessibilityReduceMotion`. (b) `Theme.faint #9D8775` on raised/well surfaces carries the smallest mono metadata (`ActivityView.swift:96`, `MediaDetailView.swift:594`, `HomeView.swift:341`) at ~4:1 — AA-borderline for caption text; verify against 4.5:1, lift `faint` or promote to `muted`. (c) MiniPlayer close is 34pt wide (`MiniPlayerView.swift:56-59`) — below 44pt on the horizontal axis. (d) EPUB reader Light/Sepia (`EbookReaderView.swift:79-103`) breaks the Dark-Only Rule — defensible as reading *content*, but document it as an explicit exception, not drift.

## Persona Red Flags

- **Alex (power):** 22-link admin wall, no search (`SettingsView.swift:73-208`); "Load more" instead of infinite scroll (`LibraryView.swift:394`); Activity queue N+1 per-media fetch (`ActivityView.swift:206-225`) — big queue visibly slow.
- **Jordan (first-timer):** cold `https://your-rawkoon-server` field, no help, no onboarding (`LoginView.swift:36`). Brick wall on first launch.
- **Sam (a11y):** fixed-34pt captions clip; segmented controls truncate; `faint`-on-dark metadata ~AA-borderline. Positives: BookCover `accessibilityHidden` in player, scrubber has real `accessibilityValue` (`PlayerView.swift:111,199`).
- **Casey (distracted mobile):** 3s toast auto-dismiss is the biggest miss; mini-player is the thumb-friendly counterpart to top-of-sheet player controls, so that part is fine.
- **Household browser (non-admin, project persona):** mostly well served — admin surfaces cleanly gated by isAdmin. One real failure: the book-search dead end (P2).

## Minor Observations

- Deprecated one-arg `onChange { tab in }` alongside two-arg form in MediaDetailView (`:114,118`) — linter nit.
- `ContinueListeningView.swift:20-32` documents and works around the known empty-`if` `.task` trap — good, matches project memory.
- Info and error toasts share the same 3s timing — error deserves longer.
- 182 `Text("...")` literals are catalog-extractable; the real localization gap is String-typed custom components (known, ~310 strings).

## Questions to Consider

1. The Player is the peak but motionless — if the "one lamp" is the core metaphor, should the apricot ever actually *glow* (breathe on play, dim on pause)? Right now the lamp is painted, not lit. (Behavior-freeze makes this a "later.")
2. Does a Light/Sepia reader theme quietly concede that "dark-only" is a chrome rule, not a product conviction?
3. Is the "household member who only browses and listens" actually first-class, or someone the admin hands a finished, logged-in phone to? Their two failures (book request, server URL) both assume the latter.
4. For a download manager whose job is long-running work that fails in interesting ways, is the toast the wrong primary error surface entirely — should failures always land in the notifications list?
