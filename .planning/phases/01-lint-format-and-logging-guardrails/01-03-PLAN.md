## The per-site disposition table

LOG-02 allows either a log call or a reason comment at each site, and the choice is a
judgment made per site rather than a rule applied to a file. Nine `try?` occurrences are
in scope for the phase; plan 01-02 owns the one in `ChapterDownloader.swift`, and this
plan owns the eight below. Line numbers are from the planning-time grep at `63dad50` and
will have moved by SwiftFormat's pass — locate each by its surrounding code, not by line
number.

| # | File | Site | Disposition | Why |
|---|---|---|---|---|
| 1 | `FileStore.swift` | `size(url:)` — reading file attributes inside a multi-clause `guard` | **comment** | The function returns an optional and a missing or unreadable file is its documented `nil` result; every caller already coalesces the nil. Converting would restructure a `guard` chain to report a condition the return type already expresses. |
| 2 | `FileStore.swift` | `delete(url:)` — removing a single file | **comment** | Best-effort removal of a file that may already be gone. A failure here is indistinguishable from success from the caller's point of view, and logging it at error severity would produce noise on a path that succeeds routinely. |
| 3 | `FileStore.swift` | `deleteEdition(_:)` — removing the edition directory | **log**, `Log.download.error` | The line above it is an explicit existence check, so a throw means the directory *does* exist and could not be removed. The user asked to free disk space and it silently did not happen — exactly the class of bug with no other signal. |
| 4 | `FileStore.swift` | `excludeFromBackup(_:)` — setting the backup-exclusion resource value | **comment** | Best-effort iCloud-backup-exclusion flag. A failure only inflates backup size; it never affects playback or download correctness. |
| 5 | `FileStore.swift` | `createDirectoryIfNeeded(_:)` — creating a directory | **log**, `Log.download.error` | Creating with intermediate directories makes "already exists" a non-error from the filesystem's own point of view, so anything thrown here is a real problem — permissions, or a full disk — and every download into that directory will fail afterwards with no other trace. |
| 6 | `AppModel.swift` | `refreshGrants(editionId:)` — the manifest refetch in the `guard let ... else { return }` | **log**, `Log.download.error` | This is the dead end the method's own doc comment describes: without a refresh the plan pumps the same dead URL forever, and a rotated server secret makes every refetch land on the same wall. A silent return is precisely how that becomes undiagnosable. |
| 7 | `AudiobookPlayer.swift` | session teardown — deactivating the audio session with the notify-others option | **log**, `Log.playback.error` | A failed deactivation means other apps are never told they may resume — a user-reported-class symptom whose only current signal is the user noticing their podcast never came back. |
| 8 | `AudiobookPlayer.swift` | `loadArtwork(from:)` — the data fetch inside the multi-clause `guard` in the artwork task | **log**, `Log.playback.error` | A failure here is a blank Lock Screen cover, which is exactly what the method's own comment says it exists to prevent. This is the one site that needs a control-flow change, and it is the site to be most careful with. |

Four logged, four commented. Adding the download-failure line from plan 01-02, the phase
adds five log call sites in total.

## Decisions adopted in this plan

| # | Question | Position adopted | Why |
|---|---|---|---|
| D-M | Does the grant-refresh catch surface an error to the user? | **No. It logs and returns, and does not touch the user-facing error message.** | The existing `guard ... else { return }` returns silently. The method already sets user-facing text on a *different* branch — the attempts-exhausted one — and adding text on this branch would put a new message on screen in a phase whose acceptance test is that nothing looks different. |
| D-N | How is the artwork-fetch site converted without changing behaviour? | **Hoist only the fetch out of the multi-clause guard into a `do`/`catch` that logs and returns; leave the remaining clauses and their order untouched.** | This is the one site where LOG-02 cannot be satisfied without a control-flow change, and it sits in the playback path that criterion 5 names as the phase's behaviour risk. Hoisting only the throwing clause keeps the cancellation check and the image decode evaluating in the same order, on the same conditions, with the same early return — the two states that differ before and after are "threw" and "did not throw", which the original collapsed into one. |
| D-O | Is the playback-path conversion allowed at all, given the behaviour constraint? | **Yes, and it is the phase's declared risk.** | Roadmap criterion 5 names it explicitly and pairs it with a device check: play, pause and resume a downloaded chapter on the TestFlight build. That check is the gate, and it is task 3's human check rather than something inferred from a green build. |
| D-P | Does this plan touch any of the other 47 `try?` sites in the target? | **No.** | RESEARCH.md scopes "the download and playback path" to these four files, and its warning is concrete: a plan that converts all of them multiplies the behaviour risk in files — the ebook reader, the home screen, the debug harness — that this phase's own risk note does not cover, for no requirement benefit. |
