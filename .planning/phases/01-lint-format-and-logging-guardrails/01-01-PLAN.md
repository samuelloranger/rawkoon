regression is rejected before the expensive macOS `build` job spends a runner minute

## Decisions adopted in this plan

There is no CONTEXT.md for this phase. Each open question below is closed here as an
explicit, stated assumption rather than left for the executor.

| # | Question | Position adopted | Why |
|---|---|---|---|
| D-A | Does `--strict` gate the `lint` job from day one? | **No. `--strict` stays off this phase.** | `--strict` fails the whole invocation on *any* warning of *any* rule. A measurement run against this tree (below) reports 136 warnings across ~15 rules. It is also structurally incompatible with LINT-02's warning-only size rules, whose whole purpose is to ratchet down over seven phases rather than gate immediately. Roadmap criterion 2 asks for zero **error**-severity violations, not zero warnings — non-strict is the only reading consistent with it. What would later turn it on: a follow-up (named in neither the v1 nor v2 requirement list) to drive the warning count to zero, then flip `strict: true`. Record it as a deliberate deferral, not a silent skip. |
| D-B | What `file_length` warning value? | **1500.** | Roadmap mandates [1443, 1600]. 1443 is `MediaDetailView.swift`'s exact current length. 1500 is round, leaves a 57-line buffer that is too small to hide growth, and is the value Phase 6 (VM-04) will ratchet down from. |
| D-C | What `type_body_length` / `function_body_length` values? | **Measured on macbuild in Task 1, then rounded up by a stated rule.** Never guessed. | SwiftLint's own line-counting algorithm is the only correct source and it must run. The rule is fixed here so the measurement mechanically produces the number: `type_body_length` = worst measured span rounded up to the next 100; `function_body_length` = worst measured span rounded up to the next 25. A Linux SwiftLint 0.63.2 pre-measurement taken at planning time gives 1325 and 76 (→ 1400 and 100) as the *expected* answer; macbuild's SwiftLint 0.65.1 is authoritative and the task must use what it prints. |
| D-D | Which runner does `lint` use? | **`ubuntu-latest`**, matching the `kit` job's tier. | Both tools have current `x86_64_linux` Homebrew bottles (verified against the formulae API: swiftlint 0.65.1, swiftformat 0.63.0), and neither needs Xcode or a compile. Cost consequence: a macOS runner bills at a 10x multiplier for a job that reads source text. Correctness consequence, and the reason D-E exists: SwiftLint on Linux **skips** rules that require SourceKit, emitting a stderr warning nobody reads. That silent under-enforcement is neutralised by D-E rather than by paying for a macOS runner. Fallback if a future SwiftLint release skips more than the one rule D-E names: change `runs-on` to `macos-26` — a one-line edit. |
| D-E | What to do about the SourceKit-dependent rules Linux skips? | **Disable `statement_position` explicitly in `.swiftlint.yml` with a reason comment.** | Exactly one rule is skipped today (measured). Disabling it in the config makes the CI runner, macbuild and a developer's local run produce *identical* results, and moves the trade-off from an invisible stderr line into a file a human reads — which is the whole point of LINT-04. |
| D-F | Opt in to `unused_import`, as RESEARCH.md suggested? | **No.** | `unused_import` is a SwiftLint **analyzer** rule: it requires `swiftlint analyze` driven by a compiler log, not `swiftlint lint`. Listing it under `opt_in_rules` for a `lint` job would be inert. This plan opts in to no rules at all and says so. |
| D-G | Apply SwiftFormat's default rule set wholesale? | **No — disable `redundantSwiftUIGroup` and `redundantViewBuilder`.** | A dry run on macbuild reports 44 of 54 files needing formatting, and the fired-rule inventory includes `redundantSwiftUIGroup` (51 sites) and `redundantViewBuilder` (2 sites). Both delete wrappers that change a SwiftUI view's **static type**, which SwiftUI uses for identity, diffing and transitions. RESEARCH.md's assumption that the default set is "almost entirely whitespace/ordering" is falsified by that measurement. This milestone's hardest constraint is no user-visible change, including layout — so these two are disabled with reasons, and every other fired rule (layout, ordering, literal formatting, pattern hoisting) stays on. |
